+## 项目名称：供应链控制塔实时数据平台建设
+
+**项目背景：** 公司硬件供应链覆盖采购、仓储、物流、维修、交付全链路，涉及旭日体系下 PMS/WMS/TMS/OMS 等 13 个业务子系统，业务形态包括销售类（骑行/充电宝/取餐柜的采购-入库-出库-交付）和资产运营类（设备投放-运维-回收-报废的全生命周期管理）。供应链控制塔（SCCT）定位为一线作战工具而非管理层报表，使用者覆盖仓管、采购、物流、维修等数百名一线操作人员，数据的用途从"看趋势"变为"指导当下每一个动作"——采购员根据实时到货进度判断是否需要催单，仓管根据实时库存水位决定是否触发补货，维修人员根据工单流转状态调整优先级。这对实时数据平台提出了三个核心要求：全链路数据必须贯通（13 个子系统的数据汇聚到统一视图）、异常必须实时感知（而非 T+1 发现）、数据必须准确可信（一线人员看到矛盾数据就不信任系统）。
+
+**技术栈：** Flink / Flink SQL、Apache Paimon（deduplicate/aggregation merge-engine、sequence.field、Changelog 流读、Lookup Join）、Kafka/Mafka、Doris、Spark SQL、HDFS
+
+**职责描述：** 负责控制塔实时数据平台的整体架构设计与核心场景落地，包括全链路数据贯通、实时监控与预警、指标体系建设，以及数据质量和链路稳定性保障体系的搭建。
+
+**技术方案：**
+
+- **场景一：全链路数据贯通与统一底座。** 控制塔需要将 13 个子系统的数据汇聚到统一视图，但各系统的 Binlog 格式、更新频率、数据模型差异极大，原方案中去重依赖 Flink ROW_NUMBER() 全局排序 + Redis 缓存时间戳做乱序判断，State 膨胀严重且每条数据一次 Redis 网络 I/O，维度数据分散在 Redis/Cellar/MySQL 三套存储中，不同系统的维表更新方式各异，关联逻辑散落在各个 Flink 任务中导致一致性难保障。新方案引入 Paimon 构建统一数据底座：ODS 层各系统 Binlog 通过 Flink CDC 写入 Paimon 主键表（deduplicate merge-engine + sequence.field），利用 LSM Tree 写入时按 event_time 自动去重和乱序过滤，Flink 端完全无需维护去重状态；维度数据统一收口至 Paimon 维表，事实表通过 Lookup Join（Local PrimaryKey Partial Lookup 模式）进行关联，基于 LSM Tree 有序性按需加载对应 Bucket 文件做定位查找，关联延迟从 Redis 毫秒级（含网络 RT）降至本地微秒级。整体实现了 13 个子系统数据从"各自为政"到"统一存储、统一关联、统一消费"的收口。
+
+- **场景二：采购执行实时监控与异常预警。** 采购业务涉及从 PO 下达→供应商确认→发货→到货→质检→入库的完整流程，原来采购员只能通过 T+1 报表了解前一天的到货情况，无法实时感知供应商交期延迟、到货数量差异、质检异常等问题，往往等问题积累到影响产线才被发现。新方案基于 Paimon Changelog 流读构建采购执行实时监控：DWD 层采购订单明细写入 Paimon 主键表后，下游监控任务通过 Changelog 流读消费变更数据（每次 Checkpoint 生成快照，流读消费两个快照间的差异），对关键节点进行规则判断——到货时间超过承诺交期触发延迟预警、实际到货数量与 PO 数量偏差超阈值触发差异预警、质检不合格率超标触发质量预警。同时 Paimon 表支持 SQL 点查和 Time Travel 回溯，采购员可以直接查询任意时间点的订单状态快照定位问题，问题排查从"逐层翻 Kafka 日志"变为"一条 SQL 定位到具体分区和时间点"。
+
+- **场景三：库存实时水位监控与预警。** 仓管人员需要实时掌握各仓库、各物料的库存水位，以便在库存低于安全水位时及时触发补货、库存积压时及时预警。但库存数据来自 WMS（入库/出库/调拨）和 INV（盘点/冻结/解冻）两个系统，每条库存变动都是增量事件，原方案用 Flink Cumulate Window 做天粒度滚动聚合，窗口状态随时间线性增长，Checkpoint 膨胀严重且依赖 Watermark 处理乱序。新方案采用 Paimon Aggregate Table（aggregation merge-engine）：按仓库+物料+日期为主键，入库数量和出库数量分别配置 SUM 聚合函数，最新库存时间配置 LAST_NON_NULL，每条增量事件写入时自动与已有记录合并计算当前库存水位。Flink 端变为无状态写入，聚合类任务 Checkpoint 大小下降约 90%，且不再依赖 Watermark，乱序到达的库存变动数据也能正确合并到结果中。下游预警任务消费 Aggregate Table 的 Changelog，当库存低于安全水位或超过积压阈值时实时触发告警推送至一线仓管。
+
+- **场景四：供应链实时指标体系与决策支撑。** 控制塔驾驶舱需要为管理层提供供应链全局视角的实时指标——采购履约率、库存周转天数、设备在线率、物流配送时效、维修工单平均处理时长等，这些指标横跨多个子系统，计算逻辑涉及跨域聚合和复杂关联。原方案每个指标独立开发 Flink 任务，聚合状态各自维护，重复建设严重且口径不一致。新方案基于 Paimon 构建统一指标体系：DWD 层通过场景一的统一底座完成数据贯通后，DWS 层按指标域（采购域/仓储域/物流域/资产域）建立 Aggregate Table，将相同主键维度的多个指标聚合到同一张表中统一计算，复用底层数据避免重复建设。ADS 层将聚合结果同步至 Doris 提供 OLAP 查询服务，驾驶舱根据用户角色（BM/区域经理）灵活选择维度组合和时间粒度。同时利用 Spark SQL 对 Paimon 表进行每日离线修正：针对实时链路中可能存在的极端乱序或数据延迟导致的偏差，Spark SQL 直接读取 Paimon 主键表执行修复逻辑覆盖错误数据，修复完成后 Flink 从指定时间戳恢复增量消费，修数时间从小时级（ODS 全链路重放）缩短至分钟级。
+
+- **场景五：实时数据质量保障体系。** 控制塔的使用者是一线操作人员，数据错误直接导致错误决策（如仓管基于错误库存水位做补货决定），因此数据准确性要求极高。建设了三层数据质量保障体系：第一层，写入层保障——利用 Paimon 主键表 deduplicate merge-engine 保证主键唯一性，sequence.field 保证乱序数据不会覆盖正确数据，从存储引擎层面杜绝重复和乱序；第二层，加工层校验——在关键 DWD/DWS 节点埋入实时对账逻辑，对比 Paimon 表与上游源系统的数据条数和关键金额字段，差异超阈值实时告警；第三层，实离对账——每日离线数据产出后，自动对比实时数据快照与离线数据的核心指标，差异率控制在 0.05% 以内，超标自动触发 Spark SQL 批处理修数。同时设计了分场景修数 SOP：轻度问题（单条数据错误）直接 Spark SQL 对 Paimon 表执行 UPDATE；重度问题（某时段整批数据异常）停下游 Flink 任务 → Spark SQL 批量修复 → Flink 从指定时间戳恢复增量消费，修数资源消耗降低约 80%。
+
+- **场景六：链路稳定性与运维保障。** 控制塔作为一线作战工具，任何数据中断都会直接影响现场操作，稳定性要求极高。建设了全链路监控体系：系统层监控 Flink 任务的 Checkpoint 成功率、反压、延迟，Kafka 消费积压和分区均衡，Doris 查询 TP99；业务层监控各指标的同环比波动、断流检测、ODS-ADS 差值校验。制定了 3 分钟发现、10 分钟定位、15 分钟恢复的故障响应 SOP。在架构层面，引入 Paimon 后将整体链路组件从 7 类（Flink/Kafka/Doris/Redis/Cellar/MySQL/HBase）收敛至 4 类（Flink/Paimon/Doris/Spark），外部组件依赖减少 60%，运维复杂度大幅降低。同时通过架构升级实现 Flink 任务无状态化——去重、乱序过滤、聚合等原来依赖 Flink State 的逻辑下沉到 Paimon 存储层，Flink 变为纯计算编排层，任务故障恢复从"等 State 恢复"变为"直接重启从最新快照消费"，恢复速度提升 70%。核心链路实现分钟级故障自愈。
+
+**项目成果：**
+- 打通 13 个子系统数据，构建供应链全链路统一实时数据底座，支撑控制塔一线作战看板上线
+- Flink 去重算子 State 降为零，相关任务 Checkpoint 大小下降 75%
+- 聚合类任务 Checkpoint 大小下降 90%，任务恢复速度提升 70%
+- Kafka Topic 数量减少 40%，中间态数据从不可查变为支持 SQL 点查和时间旅行
+- 修数时间从小时级缩短至分钟级，修数资源消耗降低 80%
+- 链路组件从 7 类收敛至 4 类，外部组件依赖减少 60%
+- 实时与离线数据差异率 < 0.05%，核心链路稳定性 99.9%
