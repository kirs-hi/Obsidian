
## 一、简历项目描述（建议写法）

### 项目名称：供应链实时数仓体系建设

**项目背景：** 公司零售/社区电商业务快速发展，供应链涵盖采购、仓储、物流、交易、售后全链路，业务对实时数据的依赖度极高——供应商需实时掌握商品售卖情况做好次日供货管理，仓库和物流人员需实时监控收货、库存、出库和人效，运营需实时观测经营指标做出决策调整。原有数仓架构存在数据时效性差（分钟级甚至T+1）、实时与离线数据一致性低、生产链路耦合度高导致稳定性不足等问题。

**职责描述：** 负责供应链实时数仓的整体架构设计与核心模块开发，涵盖数据采集、实时加工、OLAP服务、质量保障四大模块。

**技术方案：**

- **数据架构：** 基于 Lambda 架构演进，采用 Flink + Kafka + Doris 为核心技术栈，设计 ODS → DWD → DWS → ADS 四层实时数仓分层体系。根据时效性和数据量级灵活选择流引擎（Flink SQL，秒级）、批引擎（Doris2Doris，分钟级）和 Blade 引擎（解决大状态问题），实现流批结合的生产模式。
- **==性能优化==：** 按业务过程（支付/退款）、数据粒度（订单/订单商品）、数据源时效性进行任务拆分，将核心链路 Flink State 从 8.5G 降至 1.8G（降低 80%），CPU 使用率从 58% 降至 15.8%（降低 73%）。通过算子粒度 TTL 精准配置、SQL 拓扑优化（避免列裁剪导致算子翻倍）等手段持续优化资源消耗。

## 三、面试深挖问答要点（按模块准备 2-3 个可展开的技术点）

### 模块一：数据架构设计

**Q: 为什么选择流批结合而不是纯流处理？**

供应链业务场景复杂，不同场景对时效性要求不同。纯流处理在复杂 ETL（3 个以上流关联、天级时差）场景下开发难、运维难、稳定性差。批引擎（Doris2Doris）开发效率高、运维方便、去重方便，适合准实时场景。我们根据时效性要求、数据量级、模型复杂度三个维度做引擎选型决策：秒级 + 大数据量 → 流引擎；分钟级 + 中等数据量 + 复杂 ETL → 批引擎；秒级 + 大状态 → Blade 引擎。

**Q: Blade 引擎是怎么解决大状态问题的？**

Flink 作业状态缓存在内存中，状态过大会导致 Checkpoint 失败、OOM。Blade 是分布式数据库，支持水平扩展、高并发写入、Binlog 收集。方案是：多流不在 Flink 内做 Join，而是各自只更新 Blade 表中对应字段，通过 Blade Binlog 收集重新转为流，实现"存储层关联"替代"计算层关联"。

### 模块二：数据准确性

**Q: 流式聚合中间态不确定性怎么解决的？**

订单商品明细数据逐条到达时，聚合结果会频繁变化。我们的方案是在上游整合订单整体粒度的价格信息，在聚合时通过判断"商品金额求和 ≈ 订单金额"（容差 10 元）来判断数据是否到齐，到齐后才下发，保证结果确定性。

**Q: 长周期退款关联怎么做的？**

99.9975% 的退款发生在支付后 6 个月内。方案是：正向支付数据同时写 Kafka 和 Cellar 缓存（保留 6 个月），退款流同时关联实时流和缓存（以流为主，未关联上再查缓存）。历史数据用离线数据初始化，每日用离线数据修正，避免实时数据偶发丢失。关联成功率从 96.55% 提升到 99.997%。

**Q: Doris 数据乱序怎么解决的？**

Kafka→Doris 的 Stream Load 是分批导入，同一批次内 Replace 聚合方式替换顺序不保证。引入 Doris Sequence 列，值 = 业务更新时间 + 系统处理时间，较大值替换较小值。正逆向合流场景中，退款流的 Sequence = 支付流更新时间 + 退款流更新时间 + 系统处理时间，保证退款数据的 Sequence 一定大于支付数据，避免正向数据覆盖退款数据。

### 模块三：稳定性保障

**Q: 双链路热备怎么做的？**

主备链路从 Binlog 采集开始完全独立，部署在不同机房（如云谷 vs 兆丰），Kafka 集群、Yarn 队列、Doris 集群全部物理隔离。主备链路保持代码版本和配置完全一致。通过主备链路差值监控判断是否可以切换，故障时在降级预案平台一键切换。

**Q: Flink 任务调优有哪些经验？**

三个关键点：一是 State TTL 精准配置（算子粒度而非作业粒度），左右流关联时根据流的更新频率差异设置不同 TTL，State 减少 80%；二是避免 Flink 列裁剪导致算子翻倍（Union All + 多 Sink 场景），通过合并数据源、保持 Sink 字段一致来削减算子数量，性能提升 6 倍；三是升级 Flink 1.12 + 调大 JVM Overhead 内存比例（30%-40%）解决 Container 内存超用被 Kill 的问题。

### 模块四：实时离线一致性

**Q: 怎么保证实时和离线数据一致？**

三层保障：事前——实时和离线 RD 在首次开发前对齐建模细节和字段命名，变更后统一记录并通知对方；事中——工具化监控实时模型和离线模型的数据差异；事后——出现不一致时分析原因，修正机制漏洞。特殊场景（如物理删除、数据时效追踪）允许实时模型新增标志字段，但需记录差异原因。

#标签 面试官问题

**第一块：架构设计与选型判断。** 这是面试官最先关心的，用来判断你是"执行者"还是"设计者"。典型问题包括：为什么选 Flink 而不是 Spark Streaming？流批结合架构里，哪些场景用流、哪些用批，判断依据是什么？实时数仓为什么要分层，DWD 和 DWS 的边界怎么划？为什么选 Doris 做 OLAP 引擎，和 ClickHouse 比有什么取舍？回答这类问题的关键是讲清楚"约束条件"——不是说某个技术好，而是在你的业务场景、数据量级、时效性要求下，这个选择是最合理的。

**第二块：Flink 技术深度。** 这是数据开发岗的硬核考察区，面试官会从你简历里的具体细节往下挖。比如：State 从 8.5G 降到 1.8G 具体怎么做的？TTL 怎么配的，配错了会有什么后果？数据乱序怎么处理的，Watermark 策略是什么？Checkpoint 失败排查过吗，常见原因有哪些？大状态场景下 RocksDB 调优做过哪些？反压怎么定位和解决？这类问题没有捷径，需要你对 Flink 的状态管理、时间语义、Checkpoint 机制、反压机制有扎实理解。建议你重点回顾优选物流稳定性治理和配送 Flink 性能优化那两篇文章里的细节。

**第三块：数据准确性与一致性。** 面试官非常喜欢问这个，因为它能区分"做过实时"和"做好实时"的人。常见问题：实时和离线数据对不上怎么排查？你们的一致性是怎么保证的？长周期退款关联 99.997% 是怎么算的，剩下的 0.003% 是什么情况？乱序数据怎么处理，Sequence 列的原理是什么？上游数据延迟或丢数了怎么办？回答时要体现你有一套系统化的方法论，而不是"遇到一个修一个"。你简历里写的"事前对齐、事中监控、事后改进"这个框架很好，面试时展开讲就行。

**第四块：稳定性与故障处理。** 这块考察的是你的工程成熟度和线上经验。面试官会问：讲一个你印象最深的线上故障？3-10-15 的故障响应机制具体怎么运作的？跨机房双链路热备怎么做的，切换时数据会不会丢？降级预案具体是什么，举个例子？700+ 任务的 SLA 99.9% 怎么保障的？这类问题最好用"故事"来回答——某次出了什么问题、你怎么发现的、怎么定位的、怎么修的、后来做了什么防止再发生。

**第五块：数据治理与规范化。** 这块在高级别面试中权重更大，考察你的体系化思维。比如：实时数仓的命名规范和建模规范是怎么定的？上线检测工具具体检查哪些项？怎么推动团队遵守规范的？监控告警覆盖度 90% 是怎么衡量的，剩下 10% 是什么？数据质量问题的分类体系是怎么建立的？

**第六块：业务理解。** 面试官会穿插着问你对供应链业务的理解，判断你是不是只写 SQL 不懂业务。比如：供应链的核心数据指标有哪些？采购、仓储、物流、交易这几个环节的数据流是怎么串起来的？实时数据在供应链里最核心的应用场景是什么？这块不需要你讲得多深，但要让面试官感觉你理解数据背后的业务含义，而不是把自己定位成"写 Flink 任务的"。

总结一下优先级：如果你面的是 P6-P7 级别，重点准备第二块（Flink 深度）和第三块（准确性）；如果面的是 P7+，第一块（架构选型）和第四、五块（稳定性、治理）的权重会明显上升。建议你针对每一块准备 2-3 个可以讲 3 分钟的完整案例，比泛泛而谈有效得多。

## 面试要点梳理

基于以上 19 篇文章的内容，我按面试追问的逻辑链条整理要点。面试官通常的追问路径是：**架构全貌 → 某个模块深挖 → 遇到什么问题 → 怎么解决的 → 效果如何**。

### 一、架构设计类（必问）

**Q: 你的实时数仓整体架构是怎样的？**

四层分层：ODS（Binlog/日志接入）→ DWD（清洗、过滤、关联、扩维）→ DWS（跨域关联、聚合）→ ADS（面向分析主题）。维度层用 Redis/Tair 存储，离线数据初始化 + 实时更新。数据流转通过 Kafka，服务层用 Doris 做 OLAP 查询。（来源：文章 1、2、5）

**Q: 为什么选择流批结合而不是纯流？**

三个原因：一是供应链业务场景复杂度差异大，纯流在复杂 ETL（3+ 流关联、天级时差）场景下开发难、运维难；二是批引擎（Doris2Doris）开发效率接近离线 ETL，去重方便，适合准实时场景；三是部分场景（如商业分析宽表）对时效性要求是分钟级而非秒级，用流处理是资源浪费。选型决策框架：秒级 + 大数据量 → Flink；分钟级 + 中等数据量 + 复杂 ETL → Doris2Doris；秒级 + 大状态 → Blade 引擎。（来源：文章 2）

**Q: Doris 建模怎么选型？**

明细事实层用 Unique 模型（全局主键为 key），保证中间状态和回刷不影响一致性；汇总层如果有 SUM 聚合或跨维度去重，也用 Unique 模型；其他聚合类型用 Aggregate 模型自动聚合，减少数据量提高查询性能。（来源：文章 2）

### 二、数据准确性类（高频深挖）

**Q: 流式聚合中间态不确定性怎么解决？**

订单商品明细逐条到达时，聚合结果频繁变化，可能出现两类问题：一是商品未到齐时聚合结果不完整，二是同一商品多条更新导致重复计算。方案是在上游整合订单整体粒度的价格信息，聚合时判断"商品金额求和 ≈ 订单金额"（HAVING SUM(price) - MAX(order_price) > -10），到齐后才下发。（来源：文章 1）

**Q: 长周期退款关联怎么做？**

数据分析显示 99.9975% 的退款发生在支付后 6 个月内。方案：正向支付数据同时写 Kafka 和 Cellar 缓存（保留 6 个月历史），退款流同时关联实时流和缓存（以流为主，未关联上再查缓存）。历史数据用离线初始化，每日用离线修正。为什么不用 Flink State？状态存储量过大，任务稳定性差。为什么不用 Doris Aggr 模型多任务更新？正逆向更新同一张表存在顺序性问题，Aggr 模型不支持 Sequence 列。关联成功率从 96.55% 提升到 99.997%。（来源：文章 1）

**Q: 数据乱序怎么解决？**

三个层面保障顺序：输入源层面，按业务主键指定分区写入，不用自增 ID；加工层面，用 row_number + 排序字段（Binlog 的 execute_time + source_ip + file_name + offset）取最新记录；输出层面，设置 keyBy 参数 + should_emit_order 参数。Kafka→Doris 的乱序用 Doris Sequence 列解决，Sequence = 业务更新时间 + 系统处理时间。正逆向合流场景，退款流的 Sequence = 支付流更新时间 + 退款流更新时间 + 系统处理时间，保证退款数据永远不会被支付数据覆盖。（来源：文章 1）

**Q: 实时数据准确性问题有哪些常见类型？**

分为可控因素和不可控因素。可控的包括：代码逻辑（字段类型精度丢失、乱序风险）、业务理解（State TTL 小于业务生命周期）、数据延迟。不可控的包括：上游数据异常、大数据组件问题（Kafka 分区 Leader 切换导致乱序、Cellar 集群异常导致维度关联失败）。治理框架是事前预防（上线检测工具 + 语义检查工具 + 开发规范）、事中监控（FRD 对账 + 统计异常感知）、事后修复（分场景修数方案）。（来源：文章 8）

### 三、Flink 性能优化类（技术深度体现）

**Q: State 优化怎么做的？**

两个关键手段。第一是算子粒度 TTL 配置：默认 Flink SQL 只支持作业粒度 TTL，所有算子用同一个最大值。NAU 平台支持算子粒度配置后，对左右流关联算子根据流的更新频率差异设置不同 TTL（如订单状态流 TTL 长、订单商品明细流 TTL 短），State 从 8.54G 降到 1.8G（降 80%），CPU 从 58% 降到 15.81%（降 73%）。第二是任务拆分：按业务过程（支付/退款分离）、数据粒度（订单/订单商品分离）、数据源时效性（支付金额/WAC 成本分离）拆分，支付过程 TTL 从全生命周期缩短到 3 小时，状态降为 1/3。（来源：文章 1）

**Q: SQL 拓扑优化是什么意思？**

在多数据源整合（Union All）+ 多 Sink 输出场景下，Flink 引擎的列裁剪优化会从 Source 层针对不同 Sink 分别裁剪，导致算子数量翻 4 倍，State 暴增。解决方案：合并 Union All 逻辑，全局使用主流关联，多个 Sink 字段保持最小差异避免引擎主动列裁剪。优化后 Checkpoint 大小和消费速度提升 6 倍，资源降低 75%。（来源：文章 1）

**Q: Flink 任务 Container 被 Kill 怎么解决？**

State 使用堆外内存不受 JVM 管控，容易超出 Yarn Container 内存上限被 Kill。两个方法结合：升级 Flink 1.12（对 State 内存有更严格控制）+ 调大 JVM Overhead 内存比例（默认 25%，调到 30%-40%）。（来源：文章 9）

**Q: 大状态场景怎么处理？**

当 Flink State 过大导致 Checkpoint 失败、OOM 时，用 Blade 引擎替代。方案：多流不在 Flink 内做 Join，各自只更新 Blade 表中对应字段（单流部分字段更新），通过 Blade Binlog 收集重新转为流。选 Blade 而不选 Doris/Cellar 的原因是 Blade 同时支持水平扩展、高并发读写和 Binlog 收集（批转流）。（来源：文章 14）

### 四、稳定性保障类（体现工程能力）

**Q: 双链路热备怎么做？**

主备链路从 Binlog 采集开始完全独立，部署在不同机房（如云谷 vs 兆丰），Kafka 集群、Yarn 队列、Doris 集群全部物理隔离。主备保持代码版本和配置完全一致。通过主备链路差值监控判断是否可切换，故障时在降级预案平台一键切换。代价是资源翻倍 + 管理成本增加，通过任务分级保障（只对核心任务做双链路）来控制成本。（来源：文章 9、10）

**Q: 全链路监控怎么设计？**

分系统告警和业务告警两层。系统告警包括：Kafka 积压/断流、Flink 延迟超 10 分钟/状态异常/Checkpoint 失败/频繁重启、Doris 慢查询。业务告警包括：ODS 层同环比（判断 Binlog 采集是否异常）、ADS 层同环比（判断链路是否异常）、主备链路差值（判断某条链路是否故障）、ODS-ADS 差值（验证链路数据完整性）、业务指标定制化监控（如超时单占比、人均负载等合理区间告警）。目标是 3 分钟发现、10 分钟定位、15 分钟恢复。（来源：文章 10）

**Q: 性能压测怎么做？**

供应链业务有"集单"场景（固定时间点批量下发订单，单表 QPS 可达 4W+，持续约 5 分钟）。压测方法：用线上未使用的备用链路，基于 Kafka 数据回溯能力回放 ODS/DWD 层数据，按峰值 1.5 倍系数压测。观察指标：消费组积压、数据抖动、Checkpoint 连续失败、反压长时间高位、内存指标。配合周期性压测计划及时调整参数。（来源：文章 9）

### 五、实时离线一致性类（体现规范意识）

**Q: 怎么保证实时和离线数据一致？**

三层闭环：事前——实时和离线 RD 首次开发前对齐建模细节和字段命名，变更后统一记录并通知对方；事中——工具化监控实时和离线模型数据差异；事后——出现不一致时分析原因、修正机制。特殊场景允许差异但需记录：物理删除（实时模型加 delete_flag 字段）、数据时效追踪（实时模型加 load_time 字段）。差异率长期控制在万分之五以下。（来源：文章 2）

### 六、业务理解类（加分项）

**Q: 实时数据在供应链中具体怎么用？**

三类场景：一是指导一线生产——仓库人员看实时收货/出库进度调配人力，网格站看实时分拣完成率保障履约时效，供应商看实时售卖情况调整次日供货；二是经营分析——管理层看实时交易大盘了解经营状况，运营看实时优惠与成本变化调整策略；三是线上服务——实时特征服务于 ETA 预估算法、推荐算法、营销策略。供应链实时数据的特殊性在于它直接参与生产决策，数据错误可能导致一线生产秩序混乱甚至公司资损，所以对准确性和稳定性的要求远高于普通 BI 分析场景。（来源：文章 1、2、8、9）
