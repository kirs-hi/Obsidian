
## 一、简历项目描述（建议写法）

### 项目名称：供应链实时数仓体系建设

**项目背景：** 公司零售/社区电商业务快速发展，供应链涵盖采购、仓储、物流、交易、售后全链路，业务对实时数据的依赖度极高——供应商需实时掌握商品售卖情况做好次日供货管理，仓库和物流人员需实时监控收货、库存、出库和人效，运营需实时观测经营指标做出决策调整。原有数仓架构存在数据时效性差（分钟级甚至T+1）、实时与离线数据一致性低、生产链路耦合度高导致稳定性不足等问题。

**职责描述：** 负责供应链实时数仓的整体架构设计与核心模块开发，涵盖数据采集、实时加工、OLAP服务、质量保障四大模块。

**技术方案：**

- **数据架构：** 基于 Lambda 架构演进，采用 Flink + Kafka + Doris 为核心技术栈，设计 ODS → DWD → DWS → ADS 四层实时数仓分层体系。根据时效性和数据量级灵活选择流引擎（Flink SQL，秒级）、批引擎（Doris2Doris，分钟级）和 Blade 引擎（解决大状态问题），实现流批结合的生产模式。
- **任务解耦与性能优化：** 按业务过程（支付/退款）、数据粒度（订单/订单商品）、数据源时效性进行任务拆分，将核心链路 Flink State 从 8.5G 降至 1.8G（降低 80%），CPU 使用率从 58% 降至 15.8%（降低 73%）。通过算子粒度 TTL 精准配置、SQL 拓扑优化（避免列裁剪导致算子翻倍）等手段持续优化资源消耗。
- **数据准确性保障：** 设计"数据等待+金额校验"机制解决流式聚合中间态不确定性问题；基于 Cellar 外存 + 实时流双路关联方案解决长周期退款数据关联（退款关联成功率从 96.55% 提升至 99.997%）；引入 Doris Sequence 列机制解决 Kafka→Doris 数据乱序问题，保障正逆向数据流合并的顺序正确性。
- **稳定性体系：** 建设核心链路跨机房双链路热备，Flink/Kafka/Doris 集群物理隔离；搭建全链路监控（ODS-ADS 差值监控、主备链路差值监控、业务指标同环比监控），实现 3 分钟发现、10 分钟定位、15 分钟恢复的故障响应 SOP。
- **实时离线一致性：** 推进实时模型与离线模型统一建模规范（统一主题域划分、统一命名、统一口径），通过事前对齐、事中监控、事后改进的闭环机制，将实时与离线数据差异率长期控制在万分之五以下。

**项目成果：**

- 核心链路半年零 P0 告警，Checkpoint 平均制作时间 < 1 分钟
- 实时与离线数据差异率 < 0.05%，退款数据关联成功率 99.997%
- 核心实时大盘 30QPS 下 TP99 < 2s
- 实时离线统一模型开发效率提升近一倍
- 700+ 实时任务稳定性达 99.9%

## 三、面试深挖问答要点（按模块准备 2-3 个可展开的技术点）

### 模块一：数据架构设计

**Q: 为什么选择流批结合而不是纯流处理？**

供应链业务场景复杂，不同场景对时效性要求不同。纯流处理在复杂 ETL（3 个以上流关联、天级时差）场景下开发难、运维难、稳定性差。批引擎（Doris2Doris）开发效率高、运维方便、去重方便，适合准实时场景。我们根据时效性要求、数据量级、模型复杂度三个维度做引擎选型决策：秒级 + 大数据量 → 流引擎；分钟级 + 中等数据量 + 复杂 ETL → 批引擎；秒级 + 大状态 → Blade 引擎。

**Q: Blade 引擎是怎么解决大状态问题的？**

Flink 作业状态缓存在内存中，状态过大会导致 Checkpoint 失败、OOM。Blade 是分布式数据库，支持水平扩展、高并发写入、Binlog 收集。方案是：多流不在 Flink 内做 Join，而是各自只更新 Blade 表中对应字段，通过 Blade Binlog 收集重新转为流，实现"存储层关联"替代"计算层关联"。

### 模块二：数据准确性

**Q: 流式聚合中间态不确定性怎么解决的？**

订单商品明细数据逐条到达时，聚合结果会频繁变化。我们的方案是在上游整合订单整体粒度的价格信息，在聚合时通过判断"商品金额求和 ≈ 订单金额"（容差 10 元）来判断数据是否到齐，到齐后才下发，保证结果确定性。

**Q: 长周期退款关联怎么做的？**

99.9975% 的退款发生在支付后 6 个月内。方案是：正向支付数据同时写 Kafka 和 Cellar 缓存（保留 6 个月），退款流同时关联实时流和缓存（以流为主，未关联上再查缓存）。历史数据用离线数据初始化，每日用离线数据修正，避免实时数据偶发丢失。关联成功率从 96.55% 提升到 99.997%。

**Q: Doris 数据乱序怎么解决的？**

Kafka→Doris 的 Stream Load 是分批导入，同一批次内 Replace 聚合方式替换顺序不保证。引入 Doris Sequence 列，值 = 业务更新时间 + 系统处理时间，较大值替换较小值。正逆向合流场景中，退款流的 Sequence = 支付流更新时间 + 退款流更新时间 + 系统处理时间，保证退款数据的 Sequence 一定大于支付数据，避免正向数据覆盖退款数据。

### 模块三：稳定性保障

**Q: 双链路热备怎么做的？**

主备链路从 Binlog 采集开始完全独立，部署在不同机房（如云谷 vs 兆丰），Kafka 集群、Yarn 队列、Doris 集群全部物理隔离。主备链路保持代码版本和配置完全一致。通过主备链路差值监控判断是否可以切换，故障时在降级预案平台一键切换。

**Q: Flink 任务调优有哪些经验？**

三个关键点：一是 State TTL 精准配置（算子粒度而非作业粒度），左右流关联时根据流的更新频率差异设置不同 TTL，State 减少 80%；二是避免 Flink 列裁剪导致算子翻倍（Union All + 多 Sink 场景），通过合并数据源、保持 Sink 字段一致来削减算子数量，性能提升 6 倍；三是升级 Flink 1.12 + 调大 JVM Overhead 内存比例（30%-40%）解决 Container 内存超用被 Kill 的问题。

### 模块四：实时离线一致性

**Q: 怎么保证实时和离线数据一致？**

三层保障：事前——实时和离线 RD 在首次开发前对齐建模细节和字段命名，变更后统一记录并通知对方；事中——工具化监控实时模型和离线模型的数据差异；事后——出现不一致时分析原因，修正机制漏洞。特殊场景（如物理删除、数据时效追踪）允许实时模型新增标志字段，但需记录差异原因。
