
## 一、简历项目描述

> 本文件是全新版本的实时数据项目简历，核心视角是"供应链数据分析能力建设"——不讲怎么建实时数仓、也不讲怎么做架构升级，而是讲在供应链业务从"数据线上化"走向"数据驱动决策"的过程中，怎么用 Paimon 解决跨系统数据整合与实时分析的核心痛点。与已有两个版本形成差异化：版本1讲基建（Flink+Kafka+Doris），版本2讲升级（引入Paimon做架构优化），本版本讲应用（Paimon支撑供应链分析能力从无到有）。

### 项目名称：供应链实时数据分析能力建设

**项目背景：** 公司硬件供应链覆盖骑行设备、充电宝、备件等多条产品线，后端运营依赖旭日系统串联 PMS（采购）、WMS（仓储）、TMS（物流）、MMS（维修）、OMS（订单）等 13 个业务子系统。前期数据建设聚焦于"线上化"——各子系统独立产出 T+1 离线报表，数据分散在各自的 Hive 表和 MySQL 中。随着业务进入精细化运营阶段，管理层提出构建供应链数据分析能力的诉求：一是需要跨系统的实时指标体系（成本、质量、效率、满意度四个维度），二是需要统一的数据口径消除 13 个子系统各自统计导致的"数出多门"问题，三是一线操作人员需要秒级看到自己的作业数据用于实时决策。核心挑战在于 13 个子系统的数据模型、更新频率、主键体系各不相同，传统的 Flink+Kafka 实时链路在跨系统数据整合场景下面临维度数据分散、口径难统一、修数成本高三大瓶颈。

**职责描述：** 负责供应链实时分析层的数据架构设计与核心场景落地，主导跨系统数据整合方案、实时指标体系建设和 Paimon 技术选型与实施。

**技术方案：**

- **==场景一：跨系统维度数据统一收口==：** 旭日 13 个子系统的维度数据（设备主数据/仓库信息/供应商信息/物流网络/维修站点等）原来分散在 Redis、Cellar、MySQL 三套存储中，各系统独立维护，更新频率从秒级（设备在线状态）到天级（供应商资质）不等，事实表关联时需要在每个 Flink 任务中分别编写对不同存储的 Lookup 逻辑，关联逻辑散落在数十个任务中，一旦某个系统的维度发生变更（如 WMS 仓库编码调整），需要逐个任务排查和修改，且不同存储的更新延迟不一致导致同一时间点查到的维度数据版本不同，下游分析指标出现矛盾。新方案将全部维度数据统一写入 Paimon 维表，采用 Lookup Join（Local PrimaryKey Partial Lookup 模式）替代原有的多源异构关联。Paimon 维表基于 LSM Tree 有序性做定位查找，事实表关联时直接本地读取，无需网络 I/O；维度变更只需更新 Paimon 一处，所有下游任务自动获取最新维度。维表管理从"各自为政"变为"一处更新、全局生效"，维度关联的外部组件依赖从三套（Redis/Cellar/MySQL）收敛为一套（Paimon），维度变更的全链路生效时间从小时级（需逐个任务重启）缩短至分钟级（Paimon 快照刷新周期）。

- **==场景二：多系统事实数据去重与乱序治理==：** 构建跨系统分析指标（如全链路履约时效：从 PMS 采购下单 → WMS 入库 → TMS 物流签收 → MMS 设备激活的端到端时间）需要整合多个子系统的事件流。各系统的 Binlog 时间戳精度不同（有的是毫秒、有的是秒），经过 Kafka 多分区传输后乱序加剧，同一业务实体（如一台设备）在不同系统中的事件到达顺序无法保证。原方案依赖 Flink ROW_NUMBER() 窗口函数做去重、Redis 缓存时间戳做乱序过滤，每条数据一次 Redis 网络请求，且 Redis 状态与 Flink Checkpoint 无法联邦，故障恢复后存在状态不一致风险。新方案采用 Paimon 主键表（deduplicate merge-engine）+ sequence.field 机制：以业务实体主键（如设备编号+事件类型）定义 Paimon 主键，sequence.field 设为各系统统一换算后的事件时间戳，Paimon 在 LSM Tree Compaction 阶段自动按 sequence.field 保留最新记录，乱序和重复数据在写入时即被过滤。Flink 端从"有状态去重"变为"无状态写入"，去重算子 State 降为零，相关任务 Checkpoint 大小下降约 75%；Redis 乱序判断组件完全下线，每条数据节省一次网络 I/O，高并发场景下吞吐量提升约 30%。

- **==场景三：供应链实时指标聚合下沉==：** 供应链分析的核心指标按成本（采购单价/物流成本/维修成本）、质量（设备故障率/退货率）、效率（库存周转天数/履约时效/人效）、满意度（工单响应时长/一次修复率）四个维度展开，均需要天粒度的实时滚动聚合。原方案用 Flink Cumulate Window 做天粒度聚合，窗口状态随时间线性增长（一天的数据全部缓存在 Flink State 中），Checkpoint 膨胀严重且高度依赖 Watermark——13 个子系统的数据到达速率差异大，全局 Watermark 被最慢的系统拖住，导致聚合结果延迟或数据丢失。新方案采用 Paimon Aggregate Table（aggregation merge-engine），按指标主键（日期+业务维度组合）定义聚合表，预设聚合函数（SUM 用于金额类、LAST_NON_NULL 用于状态类、MAX 用于时间戳类），每条新数据写入时自动与已有记录合并，聚合逻辑从 Flink 计算层下沉到 Paimon 存储层。Flink 端变为无状态写入，聚合类任务 Checkpoint 大小下降约 90%，任务恢复速度提升 70%；不再依赖 Watermark，天然支持 13 个子系统不同速率数据的正确聚合，彻底消除因 Watermark 推进不均匀导致的指标延迟问题。

- **==场景四：可查可回溯的分析链路与快速修数==：** 跨系统分析指标一旦出现异常，需要快速定位是哪个子系统、哪个时间段的数据出了问题。原方案的 ODS→DWD→DWS 层间用 Kafka Topic 流转，中间态数据是纯日志流，不可查不可回溯，排查问题只能从 ODS 重新消费逐层验证，耗时数小时；修数需要重跑整条链路，13 个子系统的数据全部重新处理，资源消耗巨大。新方案将层间流转从 Kafka 迁移至 Paimon 表，下游任务通过 Changelog 流读消费变更数据。Paimon 表支持 SQL 点查和 Time Travel（时间旅行回溯），排查时直接用 SQL 查询指定时间点的快照即可定位问题数据所属的子系统和时间段。修数流程也从"全链路重放"变为"定点修复"：停掉目标层的 Flink 任务 → 用 Spark SQL 直接对 Paimon 主键表执行修复逻辑（UPDATE/DELETE）→ 修复完成后 Flink 从指定时间戳恢复增量消费。Kafka Topic 数量减少约 40%，问题排查效率提升 5 倍以上（从数小时逐层回溯变为分钟级 SQL 定位），修数时间从小时级缩短至分钟级，修数资源消耗降低约 80%。

**项目成果：**
- 13 个子系统的维度数据从三套异构存储（Redis/Cellar/MySQL）统一收口至 Paimon，维度变更全链路生效时间从小时级缩短至分钟级
- 跨系统去重/乱序相关任务 Checkpoint 大小下降 75%，Redis 乱序组件完全下线
- 供应链四维指标（成本/质量/效率/满意度）聚合类任务 Checkpoint 大小下降 90%，任务恢复速度提升 70%
- 中间态数据从不可查变为支持 SQL 点查和时间旅行，修数时间从小时级缩短至分钟级
- 供应链分析口径从"数出多门"（13 个子系统各自统计）统一为"一处计算、全局一致"，数据口径不一致投诉归零
- 整体链路组件数从 7 类（Flink/Kafka/Doris/Redis/Cellar/MySQL/HBase）收敛至 4 类（Flink/Paimon/Doris/Spark），运维复杂度大幅降低

## 二、技术栈清单

| 技术 | 使用场景 |
|------|---------|
| Apache Paimon | 流式数据湖格式，维表统一存储（Lookup Join）、主键表去重/乱序过滤（deduplicate + sequence.field）、Aggregate Table 指标聚合下沉、Changelog 流读替代 Kafka 中间层、批处理修数 |
| Flink / Flink SQL | 实时 ETL 主引擎，跨系统数据整合、写入 Paimon 表、消费 Changelog 流、Lookup Join 维表关联 |
| Spark SQL | Paimon 离线批处理修数引擎，直接对主键表执行修复逻辑（UPDATE/DELETE） |
| Kafka / Mafka | ODS 层数据采集（各子系统 Binlog 接入），部分未迁移链路的层间流转 |
| Doris | OLAP 分析引擎，ADS 层查询服务，供应链分析看板底层引擎 |
| HDFS/对象存储 | Paimon 表底层存储，列式存储（ORC 格式）+ LSM Tree 索引 |

## 三、面试深挖问答

### 模块一：业务理解与数据整合（本版本核心差异点）

**Q: 旭日系统 13 个子系统的数据整合，最大的难点是什么？**

最大的难点不是技术，是"口径统一"。13 个子系统各自有一套指标定义，举个例子："库存周转天数"这个指标，WMS 系统按实物出入库时间计算，PMS 系统按采购订单确认时间计算，财务系统按成本结转时间计算，三个系统算出来的数字可以差 30% 以上。业务方看到三个不同的数，不知道该信哪个，久而久之就不信任数据了。所以我们做的第一步不是写代码，是和 13 个子系统的业务方逐一对齐指标定义，确定"唯一口径"，然后在实时层统一计算。技术上的难点反而是其次的——主要是维度数据散在三套存储里导致关联不一致，以及各系统 Binlog 时间戳精度不同导致乱序。

**Q: 为什么选 Paimon 做这件事，而不是直接在 Flink 里解决？**

Flink 在"单系统内的实时 ETL"上表现很好，但在"跨系统数据整合"场景下有两个根本性不足。第一是状态管理：13 个子系统的维度数据如果都用 Flink State 缓存，State 规模会非常大，Checkpoint 不稳定；如果用 Redis/Cellar 做外部存储，每条数据多次网络 I/O，性能和一致性都有问题。Paimon 的 Lookup Join 把维度数据统一存在一个地方，Flink 任务本地读取，既解决了一致性又解决了性能。第二是可观测性：13 个子系统的数据汇聚到一起，出了问题排查非常困难。Kafka 中间层不可查，只能从头消费逐层排查。Paimon 的每一层都支持 SQL 查询和 Time Travel，排查效率完全不同。所以选 Paimon 不是为了替代 Flink，是为了补 Flink 在"跨系统整合"场景下的短板。

**Q: 成本/质量/效率/满意度四个维度的指标体系是怎么设计的？**

这四个维度是参照供应链管理的 SCOR 模型简化而来的。成本维度主要看采购单价趋势、物流单位成本、维修单次成本，数据来源是 PMS 和 MMS；质量维度看设备故障率、退货率、来料不良率，数据来源是 MMS 和 WMS；效率维度看库存周转天数、订单履约时效、人均处理量，数据来源横跨 WMS/TMS/OMS；满意度维度看工单响应时长、一次修复率、配送准时率，数据来源是 MMS 和 TMS。每个指标都定义了实时（天内滚动）和离线（日/周/月）两个版本，实时版本用 Paimon Aggregate Table 做天粒度滚动聚合，离线版本走传统 Hive 链路，两者通过统一的指标定义文档保证口径一致。

### 模块二：Paimon 技术深挖

**Q: Paimon 主键表的 LSM Tree 结构具体是怎么工作的？**

写入时数据先进入内存的 MemTable，积累到一定大小后 Flush 为磁盘上的有序文件（Sorted Run），这是 L0 层。随着 L0 文件增多，后台 Compaction 线程将多个 Sorted Run 合并为更大的有序文件并推到更高层级，合并过程中按主键去重并执行 merge-engine 定义的合并逻辑（deduplicate/aggregation 等）。读取时需要多层合并读（类似归并排序），配合 Deletion Vectors 可以跳过无效数据加速读取。这个结构的核心优势是写入极快（顺序追加），天然支持高频更新，代价是读取需要多层合并，所以更适合写多读少的场景。

**Q: sequence.field 和 Doris Sequence 列有什么区别？**

原理类似，但作用位置不同。Doris Sequence 列解决的是"数据已经到了 Doris 之后的乱序"，属于末端兜底。Paimon 的 sequence.field 解决的是"数据在中间层流转过程中的乱序"，在写入时就保证了顺序正确性。原来的链路是 Flink → Kafka → Flink → Kafka → Doris，中间层乱序靠 Redis 判断，到 Doris 再靠 Sequence 列兜底。现在中间层换成 Paimon 后，每一层写入时就已经有序，到 Doris 时 Sequence 列变成最后一道防线而不是主要依赖。整条链路的乱序防御从"末端兜底"变为"逐层保证"。

**Q: Paimon Lookup Join 的 Local PrimaryKey Partial Lookup 模式具体怎么工作？**

和 Full Cache 模式不同，Partial Lookup 不需要启动时全量加载维表数据。它的工作方式是：当事实表的一条数据触发 Join 时，根据 Join Key 定位到 Paimon 表的对应 Bucket，然后将该 Bucket 的文件加载到本地（RocksDB 或内存），基于 LSM Tree 的有序性做定位查找。后续如果有相同 Bucket 的查找请求，直接读本地缓存。这种模式的优势是内存占用小（只缓存被访问的 Bucket），启动快，适合维表数据量大但关联热度集中的场景。代价是首次查找冷启动会慢一些。我们的场景里设备主数据有上百万条，但每个仓库关联的设备集中在几个 Bucket 里，所以 Partial Lookup 比 Full Cache 更合适。

**Q: Aggregate Table 和 Flink Cumulate Window 在效果上有什么区别？**

最终结果一样，区别在状态管理和容错机制。Cumulate Window 的状态在 Flink 内存里，窗口越大状态越大，Checkpoint 要把所有状态持久化，所以大且慢。Aggregate Table 的状态在 Paimon 的 LSM Tree 里，每条新数据写入时和已有记录合并，Flink 端无状态，Checkpoint 几乎为空。另一个关键区别是乱序处理：Window 依赖 Watermark，迟到数据要么丢弃要么侧输出二次处理；Aggregate Table 不依赖 Watermark，任何时候来的数据都会正确合并。在我们 13 个子系统数据到达速率差异大的场景下，这个优势非常明显。

**Q: Paimon 有什么局限性？**

三个主要局限。第一是时效性上限：流读时效性受 Checkpoint 间隔制约，通常 1-10 秒级，做不到 Kafka 的毫秒级，所以对延迟要求极高的场景（如风控拦截）不适合。第二是高频更新场景下的 Compaction 压力：单个 Bucket 写入 QPS 非常高时，LSM Tree Compaction 可能跟不上写入速度，导致 L0 文件堆积、读放大严重、查询变慢。我们通过合理设置 Bucket 数量分散热点 + 调大 sort-spill-threshold + 开启 async-file-write 缓解。第三是生态成熟度：Paimon 比 Hive/Iceberg 生态年轻，部分 BI 工具支持不完善，我们 ADS 层仍然用 Doris 做查询服务。

### 模块三：修数与运维

**Q: 修数流程具体怎么操作？停任务不会影响实时性吗？**

修数分四步：停掉需要修复的 DWD 层及后续 Flink 任务；用 Spark SQL 读取 Paimon 表执行修复逻辑，修复结果直接写回主键表，利用主键合并覆盖错误数据；修复完成后重启 Flink 任务并指定从某个时间戳开始消费增量数据（Paimon 支持按时间戳定位快照）；验证修复结果。确实会有短暂中断，但在供应链场景里修数通常安排在业务低峰期（凌晨），而且 Paimon 修数只需要几分钟（直接改目标表），比原来的 ODS 重放（重跑整条链路数小时）快得多。

**Q: 13 个子系统的 Binlog 时间戳精度不同，怎么处理的？**

我们在 ODS 层做了统一的时间戳归一化：所有子系统的事件时间统一转换为毫秒级 UNIX 时间戳，对于只提供秒级精度的系统（如部分老系统），在秒级时间戳后补充系统接收时间的毫秒部分作为次序区分。写入 Paimon 时 sequence.field 统一使用归一化后的时间戳字段。这样保证了跨系统比较的一致性。

## 四、和已有两个版本的区别说明

**与版本1（供应链实时数仓体系建设）的区别：** 版本1讲的是"从零搭建实时数仓基础设施"，重点是 Flink+Kafka+Doris 的分层架构设计、State 优化、数据准确性保障、稳定性建设。本版本的前提是基础设施已经有了，重点是"在基础设施之上构建跨系统的分析能力"，核心差异在于业务视角——版本1是技术导向（怎么搭平台），本版本是业务导向（怎么用平台解决分析问题）。

**与版本2（Paimon 湖仓架构升级）的区别：** 版本2讲的是"引入 Paimon 对已有架构做技术升级"，以四个技术场景为主线（去重、流读、聚合、维表+修数），是纯技术叙事。本版本虽然也用了 Paimon 的这些能力，但叙事主线完全不同——不是"为什么要升级架构"，而是"供应链 13 个子系统的数据怎么整合成统一的分析能力"。技术是手段，业务问题（数据孤岛、口径不一致、分析能力缺失）才是主线。

**面试时的使用建议：** 如果面试官对实时数仓基础设施感兴趣，展开版本1；如果追问 Paimon 技术细节，展开版本2；如果问"你做的这个事情对业务有什么价值"或者"你怎么理解数据架构为业务服务"，展开本版本。三个版本构成一个完整的叙事链：搭建基础设施 → 升级技术架构 → 构建分析能力。

## 五、注意事项

第一，本版本的核心卖点是"业务理解+技术落地"的结合。面试时不要一上来就讲 Paimon 的技术细节，先花 30 秒把 13 个子系统的数据孤岛问题讲清楚，让面试官感受到这个问题的复杂度和业务价值，再自然引出 Paimon 方案。

第二，"数出多门"是一个非常好的面试切入点。面试官问"你遇到过最难的问题"时，可以讲这个——13 个系统各自算的库存周转天数差 30%，业务方不知道信谁，你怎么定义"唯一口径"、怎么推动各方达成一致、怎么在技术上保证统一计算。这体现的是沟通协调能力和业务理解能力，比纯技术问题更稀缺。

第三，四维指标体系（成本/质量/效率/满意度）是本版本独有的业务亮点。如果面试官追问，能说出每个维度的 2-3 个具体指标、数据来源是哪个子系统、用的是 SUM/LAST_NON_NULL/MAX 中的哪个聚合函数，会非常有说服力。

第四，Paimon 技术细节的准备可以复用版本2的问答，本版本不需要重复准备。本版本面试重心应放在"业务问题 → 技术决策 → 效果衡量"的完整闭环上。
